# Frontend design

Practical reference for how the Next.js app is actually wired. For the *intent* behind the
stack choices, see [system-design.md §2, §6](./system-design.md). This file is about the
current codebase's conventions.

## Routing

```
app/
  [locale]/            en | hi — see i18n/routing.ts
    layout.tsx           root layout (html/body), fonts, Header/Footer, NextIntlClientProvider
    page.tsx              landing page
    tests/page.tsx         catalog list
    tests/[slug]/page.tsx  test detail — MedicalTest JSON-LD, generateMetadata, generateStaticParams
    packages/page.tsx      package list (no detail route yet — links back to /tests/[slug])
    book-a-test/page.tsx   booking flow
    download-report/page.tsx
    find-us/page.tsx       MedicalOrganization JSON-LD
    about/page.tsx
  admin/                NOT locale-prefixed — separate root layout, see below
    layout.tsx
    login/page.tsx
    page.tsx               dashboard
    bookings/page.tsx
    catalog/page.tsx
  sitemap.ts / robots.ts  top-level, cover both locales
```

`/[locale]` and `/admin` are **two separate root layouts** (both define their own `<html>`/
`<body>`) — this is what keeps admin routes out of the locale prefix. See
[decisions-log.md](./decisions-log.md) for why, and Next.js's "multiple root layouts" doc
(`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/next-root-params.md`) for
the mechanism.

## Next.js version note

This is Next.js 16 (`next/dist/docs/` is the authoritative reference — it's bundled per-install
and may not match training data). The two things that trip people up coming from Next 14:

- `params` and `searchParams` are always `Promise`s — `await props.params` in every page/layout.
- Use the generated `PageProps<'/route/path'>` / `LayoutProps<'/route/path'>` helper types
  instead of hand-writing `{ params: { slug: string } }`. These are ambient globals, no import
  needed, regenerated by `next dev`/`next build`.

## i18n (next-intl)

- `i18n/routing.ts` — locales (`en`, `hi`), default locale, `always` prefix strategy.
- `i18n/request.ts` — loads `messages/{locale}.json`.
- `i18n/navigation.ts` — locale-aware `Link`/`useRouter`/`usePathname`; **always import these
  instead of `next/link` / `next/navigation`** inside `app/[locale]/**` so links stay
  locale-prefixed.
- `messages/en.json` / `messages/hi.json` — flat-ish nested JSON, one key per UI string. Hindi
  strings are written natively (not machine-translated placeholders) per
  system-design.md §6 — keep it that way when adding new keys.
- Server components: `getTranslations()` / `getTranslations("namespace")` from `next-intl/server`.
- Client components: `useTranslations()` from `next-intl`.
- Bilingual **content** (test names, descriptions) is not in the message catalog — it's
  `name_en`/`name_hi` columns per row (see [database-schema.md](./database-schema.md)), picked
  at render time via `getLocale()`.

## Design tokens

Tailwind v4 — no `tailwind.config.js`. Tokens are defined in `app/globals.css` under
`@theme inline`, sourced from the palette in system-design.md §6.2:

| Token | Value | Use |
|---|---|---|
| `brand-sandstone` | `#C9A063` | Accent |
| `brand-indigo` | `#1B2A4A` | Primary dark / headings / CTAs |
| `brand-teal` | `#0F6E56` | Trust / status / links |
| `brand-paper` | `#FAF7F1` | Background |
| `brand-ink` | `#2C2C2A` | Body text |

Reference as Tailwind classes directly: `bg-brand-indigo`, `text-brand-teal`, etc.

Fonts: **Hind** (`--font-hind`, `font-sans`) for body text and all Hindi content — loaded via
`next/font/google` with `latin` + `devanagari` subsets in `app/[locale]/layout.tsx`.
**Fraunces** (`--font-fraunces`, `font-display`) for English display headlines only — apply
`font-display` explicitly, it is not the default.

The "sample journey" motif (Book → Collect → Test → Report, system-design.md §6.2) is not built
yet — earmarked for the booking flow once it's a real multi-step wizard (see
[todo.md](./todo.md)).

## Components

- `components/ui/` — design-system primitives shared by public site and admin: `Button` (+
  `buttonClasses()` for styling non-`<button>` elements like `<Link>`), `Card`, `Badge`,
  `FormField` / `inputClasses`.
- `components/layout/` — `Header`, `Footer`, `LanguageToggle` (client, toggles locale via
  `i18n/navigation`'s `useRouter`), `WhatsAppLink` (wraps `wa.me` links per
  system-design.md §4.5 — MVP has no WhatsApp API, just click-to-chat).
- `components/sections/` — landing page sections (`Hero`, `ServicesGrid`, `PopularTests`,
  `LocationMap`), each a server component pulling its own translations/data.
- `components/booking/BookingForm.tsx`, `components/reports/ReportLookupForm.tsx` — client
  components driving Server Actions via `useActionState` (React 19).

## Data layer

`lib/data/tests.ts` (`getTests`, `getTestBySlug`) checks for Supabase env vars and falls back to
`lib/data/mock-content.ts` when absent — see [decisions-log.md](./decisions-log.md). Pages call
these functions rather than querying Supabase directly, so the mock fallback is transparent to
every page that renders test data.

## Server Actions

`lib/actions/bookings.ts`, `lib/actions/reports.ts`, `lib/actions/auth.ts` — all `'use server'`,
all validate input with `zod` before touching Supabase, per the security guidance in
`node_modules/next/dist/docs/01-app/02-guides/server-actions.md` (treat every action as a public
POST endpoint, not just a function called from a trusted form).

## SEO

- `app/sitemap.ts` — generated from `routing.locales` × static paths × `getTests()`.
- `app/robots.ts` — disallows `/admin`.
- `generateMetadata` on `tests/[slug]` and `find-us` for unique titles/descriptions.
- JSON-LD: `MedicalTest` on test detail pages, `MedicalOrganization` on the find-us page. Not yet
  added to every page per system-design.md §6 ("`MedicalOrganization` + `LocalBusiness` on every
  page") — tracked in [todo.md](./todo.md) Phase 3.
